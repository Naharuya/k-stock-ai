# 케이스톡 v2.5.1 전체 점검
점검일: 2026-09-12. 대상: 현재 로컬 v2.5.1과 Entry/Exit 결측값 수정본.

## 후속 수정 상태
- P1 네 항목 수정: 데이터 부족 판정 보류, 보유목록 최신 응답 보호, 뉴스 해제·부인 문맥 분류 및 키워드 단독 Hard Stop 제거, 종합점수 결측값/완성도 검증.
- 뉴스 제목은 사실 확정 근거로 사용하지 않으며 미확인 위험은 WATCH/추가 확인 대상으로 남김. 공시·리스크로 확인된 중대 위험의 Hard Stop은 유지.
- 보유목록은 등록별 snapshotId와 요청 ID를 비교하고 최신 목록의 해당 항목만 갱신. 삭제·재등록·동시 요청을 회귀 테스트로 검증.
- 화면 숫자와 점수 이력의 결측값 처리도 보완. 입력 범위 검증, 차트 초기 이동평균 처리, 외부 API 제한시간은 후속 과제.
- 회귀 검증 명령: `npm test`. 아래 내용은 최초 점검 당시의 재현 기록이며 P1 수정 전 상태를 설명함.
- 후속 검증: `npm test` 18개 통과. Edge 데스크톱(1440px)·모바일(390px)에서 데이터 부족 표시 및 재검증 중 삭제 동작 통과. 실제 증권사 API 연동은 미검증.

## 확인된 문제와 수정 우선순위

### P1. 데이터가 없어도 Exit 결과가 보유 유지
- 위치: `src/services/entry_exit_service.js:192`.
- 재현: 진입 스냅샷에 현재 분석으로 `{ stockCode: "005930" }`만 전달하면 현재가/점수는 null인데 status=HOLD, exitPressure=0.
- 영향: 분석 실패 또는 핵심 데이터 누락이 정상 보유 판정처럼 보임. 이전 수정은 잘못된 손익 계산만 막았으며 판정의 완전성까지 해결하지는 않음.
- 수정안: 필수 데이터의 유효성·기준시각을 검증하고 DATA_INCOMPLETE/STALE 상태를 추가. 명시적 Hard Stop은 데이터 부족 상태에서도 우선 표시.
- 완료 기준: 시세·위원회·리스크가 누락되거나 오래된 경우 HOLD가 나오지 않는 회귀 테스트.

### P1. 재검증 중 변경된 보유목록을 과거 상태로 덮어씀
- 위치: `public/app.js:409`, `public/app.js:416`.
- 재현: evaluatePosition 실행 후 응답 대기 중 보유목록을 삭제하고 응답을 완료하면 삭제된 종목이 다시 저장됨. 실제 함수를 VM에 로드하고 fetch를 지연시켜 재현함.
- 영향: 삭제 취소, 신규 종목 유실, 동시 재검증 결과 덮어쓰기 가능.
- 수정안: 요청 완료 시 최신 목록을 다시 읽고 종목 ID와 스냅샷 revision이 일치하는 항목만 갱신. 삭제되거나 재등록된 항목에 대한 오래된 응답은 폐기.
- 완료 기준: 재검증 중 삭제/등록/다른 종목 동시 재검증 및 응답 순서 역전 테스트.

### P1. 뉴스 키워드만으로 해제 기사도 Hard Stop
- 위치: `src/services/news_analysis_service.js:75`, `src/services/investment_committee_service.js:135`.
- 재현: 제목이 '거래정지 해제'인 기사 한 건을 분석하면 highRiskEvents에 들어가고 committee.hardStop=true.
- 영향: 위험 해소 기사와 부정문도 위험 종목 제외로 이어짐. 공시의 Semantic Gate와 뉴스의 위험 정책이 일치하지 않음.
- 수정안: 사건 발생/부인/해소, 해당 기업과의 관련성, 출처를 구분. 단순 키워드는 검토 대상으로 표시하고 확인된 중대 사건만 Hard Stop에 연결.
- 완료 기준: 해제·부인·타사 사건은 오탐하지 않고 실제 중대 사건은 유지하는 문맥별 테스트.

### P1. 종합점수에서도 null이 유효한 0점으로 처리됨
- 위치: `src/services/investment_committee_service.js:5`, `src/services/investment_committee_service.js:131`, `src/services/full_analysis_service.js:91`.
- 재현: buildInvestmentCommittee({ completeness: { percent: 100 } })가 DATA_INCOMPLETE 대신 RISK/5점을 반환. 빠진 항목들의 weighted가 null 대신 0.
- 영향: 상위 완성도 값에 과도하게 의존해 없는 데이터를 실제 저점수로 해석. full analysis도 시장·뉴스 준비 여부만으로 완성도를 정하고, 수급 이력 부족은 기본 중립점수로 남음.
- 수정안: 숫자 파싱과 축별 READY/누락 상태를 통일하고 완성도를 실제 데이터로 계산. 없는 리스크 점수를 정상 위험으로 간주하지 않기.
- 완료 기준: 완성도 값이 100이어도 필수 축이 누락되면 판정 보류. 유효한 실제 0점은 보존.

### P2. 화면·점수 이력·차트에 결측값 0 변환이 남아 있음
- 위치: `public/app.js:21`, `public/app.js:51`, `public/app.js:92`.
- 재현: 실제 화면 숫자 함수 n(null)이 0을 반환.
- 코드 확인: 점수 이력은 Number(null)을 0으로 저장할 수 있고, 이동평균 초기 null 구간도 Number.isFinite(Number(v)) 검사를 통과해 y(0)으로 그려짐.
- 영향: 지표가 0으로 보이고 가짜 점수 하락/반등이나 차트 선이 생길 수 있음.
- 수정안: 표시용 숫자 변환의 결측값 정책 통일, 점수 미완료 시 이력 저장 생략, 이동평균 null 구간 건너뛰기.
- 완료 기준: null/빈 문자열/0 구분 테스트 및 실제 브라우저 차트 검증.

### P2. 매수 기준 입력 범위 검증 부족
- 위치: `src/services/entry_exit_service.js:50`, `src/services/entry_exit_service.js:60`, `src/server.js:196`.
- 재현: API에 quantity=-3, stopLossPct=10, takeProfitPct=-5를 보내도 HTTP 200. 수량은 1로 변경되고 뒤집힌 손실/이익 기준은 그대로 저장됨.
- 영향: 사용자가 입력 오류를 알아차리지 못한 채 예상과 다른 Exit 판정을 받음.
- 수정안: 양의 정수 수량, 유효한 매수가, 음수 손실 기준과 양수 이익 기준을 서버에서 검증하고 필드별 오류 반환. 잘못된 숫자를 조용히 기본값으로 바꾸지 않기.
- 완료 기준: 음수/소수 수량, 잘못된 종목코드, 뒤집힌 기준, 비정상 숫자 요청에 대한 API 테스트.

### P2. 외부 API 지연에 대한 응용프로그램 타임아웃 없음
- 위치: `src/services/kis_service.js:206`, `src/services/dart_service.js:35`, `src/services/news_service.js:62`.
- 코드 확인: fetch에 명시적 AbortSignal/요청 시간 제한이 없음. KIS는 전역 순차 큐를 공유하므로 한 지연 요청이 뒤 요청까지 대기시킴.
- 수정안: 공급자별 제한시간, 전체 분석 시간 예산, 취소, 요청 병합 및 실패 항목별 재시도. 진행 단계와 실패 원인을 화면에 표시.
- 완료 기준: 응답 지연/429/네트워크 오류를 주입해 정해진 시간 안에 종료되고 뒤 요청이 복구되는지 검증.
- 한계: 실제 공급자 장애를 주입하지 않았으며 이 항목은 코드 검토 결과.

## 다음 개발 아이디어
1. **데이터 품질 패널**: 각 지표의 출처, 기준일, 보고서 연도, 실시간/캐시 구분과 누락 사유 표시. 완성도와 투자매력 점수는 분리.
2. **보유 이력과 복원**: JSON 내보내기/가져오기, 삭제 취소, 매수 추가·부분 매도 기록과 평균단가. 현재 같은 종목 재등록은 이전 기준을 통째로 교체함.
3. **분석 작업 관리**: 후보 생성 단계별 진행률, 취소, 실패 종목만 재시도, 동일 종목 요청 재사용.
4. **근거 중심 상세 화면**: 점수 변화마다 실제 바뀐 재무·수급·뉴스 근거와 출처를 연결. '신뢰도 %'가 통계적 성공 확률로 읽히지 않도록 데이터 검증 수준을 우선 표시.
5. **재현 가능한 품질 검사**: npm test로 오프라인 검사를 통합하고 GitHub Actions에 연결. 클릭·저장·삭제·재검증과 모바일 차트는 Playwright로 추가 검증.
6. **연구 성능 평가**: 시점별 데이터와 후보 결과를 보존한 뒤 과거 시점에 알 수 있었던 정보만으로 순위 안정성과 후속 결과를 평가. 근거 없이 가중치부터 조정하지 않기.

권장 진행 순서: P1 네 항목과 입력 검증 → 보유 이력/복원 → 진행률/재시도 → 연구 성능 평가.
외부 사용자에게 공개 서비스로 배포할 때는 인증, 사용자별 데이터 분리, 분석 요청 제한도 추가해야 함. 현재는 로컬 사용 기준으로 점검함.
